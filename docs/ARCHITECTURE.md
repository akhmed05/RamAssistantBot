# RAM AI: архитектура и план внедрения

## Аудит исходной версии

База: main, commit 7e14694. aiogram 2.25.1, Python 3.11, OpenAI SDK 1.3.7,
httpx 0.27.2. Четыре кнопки: YouTube, AI, Apps Script, PDF. Нет авторизации,
кабинетов WB, журнала и лимитов. gpt-4 задан в коде; 404 может означать
недоступную модель или неверный endpoint, без production-логов причина не доказана.
YouTube и PDF уже были заглушками; это не новые работающие интеграции.

## Границы и роли

Telegram → проверка владельца → главный агент → инструменты выбранного кабинета
→ аналитик → контролёр → результат + журнал SQLite.

Главный агент в MVP — детерминированный маршрутизатор задач, не автономный LLM.
Команды чтения работают без OpenAI. Каждый запрос закрепляет кабинет до начала
работы. Контролёр проверяет типы/полноту данных, запрещает инструменты записи.
SQLite хранит выбор кабинета, задания, безопасные результаты, лимиты и черновики.
Ключи существуют только в переменных процесса; данные кабинетов разделены ключом
cabinet во всех таблицах. Это логическая изоляция, не отдельные базы/процессы.

| Роль | MVP | Следующий этап |
| --- | --- | --- |
| Главный агент | План, чтение, сбор результата | Очередь, составные планы, typed LLM tool calling |
| Аналитик WB | Продажи/возвраты и остатки через Statistics API | Orders, финансовые отчёты, логистика, рекомендации |
| Менеджер карточек | Черновик задачи, без WB-вызовов | Content API, SEO, diff и подтверждение |
| Рекламный агент | Черновик задачи, без WB-вызовов | Promotion API, CTR/ДРР и лимиты бюджета |
| Контент-агент | Черновик задачи | Генерация и техническая проверка изображений |
| Финансовый агент | Черновик задачи | Себестоимость, отчёты реализации, unit economics |
| Контролёр | Правила безопасности и качества | Проверка каждого типа write operation |

## Безопасность

RAM_OWNER_IDS — числовые Telegram user ID; business и платный AI доступны только
им в личном чате. Неуказанный список закрывает доступ. Кабинет 1/2 имеет собственные
ключ Statistics API и RAM_WB_N_READ_SCOPES. Read-only ограничен жёстким allowlist
двух GET endpoint; текст/LLM не задаёт URL, headers или инструмент записи.

Любые значимые изменения сейчас лишь черновики. Подтверждение владельцем
фиксирует согласование черновика, но НЕ запускает запись в WB. Следующий этап:
immutable payload + hash + кабинет + владелец + TTL → проверка контролёром →
Telegram approve/reject → atomic pending/executing transition → единственный
executor → reconciliation при неопределённом исходе. Повторять write после timeout
без сверки состояния запрещено. Никакого универсального HTTP-инструмента у LLM.

## План внедрения

1. Этот PR: авторизация, Telegram меню, два кабинета, read-only клиент, контролёр,
   журнал, persistent dedup/cache/rate/budget, configurable model, offline tests.
2. Отдельная staging-среда с отдельным Telegram-ботом и Railway volume; smoke tests
   на реальных read-only WB ключах и доступной модели OpenAI. Проверить актуальные
   endpoint, категории токенов, лимиты и полноту больших выборок по dev.wildberries.ru.
3. Полная выгрузка/пагинация и финансовые источники; не подменять оборот прибылью.
4. Карточки и реклама: typed payload, preview/diff, approval TTL, idempotency и
   recovery. Каждая операция отдельным PR и приёмочными тестами.
5. Контент и финансы; долгие задачи в durable queue, PostgreSQL/Redis для replicas>1.

Production не меняется этим PR. Слияние, смена Railway ветки и запуск — действия владельца.
